### 2.1 輸出契約（給 S7、S8a、S8c）

**`src/solver/worker.js`**

- `handleMessage(msg, post)` 是同步函式，所有回覆都經 `post` 送出；任何例外都轉成 `{type:'error', code:'INTERNAL'}`。
- 另匯出 `INIT_OPTIONS`，以及測試用的 `resetForTest`。
- 訊息協定與 §9.5 相同，細節如下：
  - `init`：必須帶 `params`（物件，少了回 `BAD_REQUEST`）。收到後依序回 6 次 `progress`，再回 `ready {tableBytes}`。之後的 `solve` 預設使用這份 `params` 中的 `metric`、`nodeLimit`、`firstNodeLimit`、`maxLength`、`phase2Cap`；`solve.opts` 可以逐欄覆寫。
  - `solve`：還沒 `init` 時回 `NOT_READY`。`fromStickerColors` 回報任何錯誤（包括規格沒列的 `COLOR_COUNT`）都回 `INVALID_STATE`，`detail` 放原本的錯誤碼。求解器的錯誤依下表轉換。成功時 `moves` 是字串陣列（view 座標）。

    | 求解器錯誤 | 回覆的錯誤碼 |
    |---|---|
    | `NODE_LIMIT` | `NODE_LIMIT` |
    | `NOT_INITIALIZED` | `NOT_READY` |
    | `UNSUPPORTED_METRIC` | `BAD_REQUEST` |
    | 其他 | `INTERNAL` |

  - `lbl`：不需要建表。先用 `fromStickerColors` 驗證狀態，不合法回 `INVALID_STATE`。`generateLbl` 回報的 `LBL_STUCK`、`INVALID_STATE`、`BAD_REQUEST` 原樣轉送；其他碼依 D-5 回 `INVALID_STATE`。
  - 未知 `type`、`id` 不是數字、或欄位缺漏，都回 `BAD_REQUEST`。

| client 方法 | 說明 |

| `cacheSize()` | 測試用 |

各流程的行為：

- **快取**（§7.5）：
  - 鍵是 `home.join('')`，值是剩下的 home 記號序列。
  - 求解結果回來時，沿著解的每一步都存一筆；筆數超過 `planCacheSize` 就丟最舊的。
  - 提示的 `planQtm` 是剩餘序列的 QTM 總和，**包含這一步**，例：`R2（2 步）· 照建議解還要 24 步`。
  - 建議解示範也先查同一個快取。
- **佇列**：
  - Worker 內同時只有一個求解請求。建表完成前（booting／building）的請求先排隊，ready 之後才送出。
  - `solveTimeoutMs` 從實際送出時才開始計算，所以建表時間不會被算進求解逾時。
  - 送新請求時，如果還有前一個請求在等待，前一個會以 `CANCELLED` 結束。
- **退回**（§9.6）：

  | 情況 | 處理 |
  |---|---|
  | `createWorker` 丟例外，或 Worker `onerror` | 轉 `mainThread`；進行中的請求改在主執行緒重跑 |
  | `initTimeoutMs` 逾時，或 init 回 `error` | 轉 `failed`，不重建 Worker |
  | `solveTimeoutMs` 逾時 | `terminate`，並在背景重建 Worker |
  | `NODE_LIMIT` | 只做本次退回，**不重建** Worker（見 §4 第 1 點） |

  本次請求的退回結果：

  | 請求 | 退回結果 |
  |---|---|
  | 提示 | 在主執行緒跑層先法，取「前面的整顆旋轉＋第一個轉動」，送 `HINT_READY {source:'lbl', planQtm:null}` |
  | 建議解示範 | `DEMO_FAILED`，`code` 為 `TIMEOUT`、`NODE_LIMIT` 或 `SOLVER_FAILED` |
  | 層先法示範 | 在主執行緒產生 |

- **主執行緒模式**：每個請求都用 `setTimer(fn, 0)` 延到下一輪才執行，讓 UI 有機會先畫出等待卡片。第一次請求時才建表，建表期間也透過 `onStatus` 回報進度。
- **取消**：
  - `cancel()` 讓等待中的 Promise 立刻以 `{type:'HINT_FAILED'|'DEMO_FAILED', payload:{version, code:'CANCELLED'}}` 結束，並回傳這個 action。UI 照常 dispatch 即可，這就是 §9.4 要求 UI 送出的那個 action。
  - Worker 之後才回來的結果不會交給任何呼叫端，但建議解仍會存進快取。
  - 下一個請求要等這個被取消的請求在 Worker 內結束後才會送出；它的 watchdog 仍然有效。
- **D-2**：`isSolvedNow(state)` 為 true 時不送請求，直接回 `code:'ALREADY_SOLVED'`。
- **失敗碼**：`failureTextKey(code)` 回傳文案鍵，S8c 依文案鍵顯示，不必依錯誤碼字串分支（與 D-6 同一精神）。

  | 回傳的文案鍵 | 失敗碼 | UI 處理 |
  |---|---|---|
  | `'demo.suggestUnavailable'` | `NODE_LIMIT`、`TIMEOUT`、`SOLVER_FAILED` | 同時提供「改看層先法示範」 |
  | `'error.invalidState'` | `INVALID_STATE`，以及所有不認得的碼（D-5） | — |
  | `'error.generic'` | `LBL_STUCK`、`BAD_REQUEST`、`NOT_READY`、`INTERNAL` | — |
  | `null` | `CANCELLED`、`ALREADY_SOLVED` | 不顯示 |

- **S8a／S8c 的呼叫方式**：先 `dispatch(HINT_REQUEST)`，再用**新的** state 呼叫 `requestHint`；`DEMO_REQUEST` 與 `requestDemo` 也是同樣順序。原因：`hint.pending` 期間 reducer 仍接受 `ROTATE`，client 以呼叫當下的 `state.orient` 換算記號，這個值必須等於 `hint.orient`。

## 4. 未預期發現

1. **ADR 與規格對 `NODE_LIMIT` 的處理不一致。** `ADR-001-solver.md` §2.6 把「單次求解逾時或 `NODE_LIMIT`」合成一列，處理是「終止並重建 Worker」；`game-spec.md` §9.6 則把 `NODE_LIMIT` 單獨列出，處理只有「本次請求退回層先法」。本段依規格實作，不重建 Worker（C-06 鎖住）。理由：`NODE_LIMIT` 是求解器正常回傳的結果，Worker 狀態沒有問題。沒有修改 docs。
2. **`hint.pending` 期間 reducer 仍接受 `ROTATE`。** client 換算記號時用的是呼叫當下的 `state.orient`，所以 S8c 一定要在 `HINT_REQUEST` 之後、下一次 `ROTATE` 之前呼叫 `requestHint`（見 §2.1 最後一點）。如果順序反了，提示會換錯座標，而且 reducer 不會拒絕。建議 S9 補一條「等待提示中轉視角」的 UI 測試。
3. **層先法示範也要等建表完成。** §9.5 規定 `lbl` 排在 `init` 之後，所以建表期間按「層先法示範」會等到 ready 才送出，最多等 `initTimeoutMs`。層先法其實可以在主執行緒 3 ms 內算完，要不要改成建表期間直接在主執行緒產生，見 §5 第 3 點。
4. **主執行緒模式的文案顯示時機。** 狀態一轉成 `mainThread`，`status().notice` 就是 true，S8c 可以在按下按鈕的當下就顯示 `mainThreadNotice`。client 用 0 ms 計時器把建表延後一輪，但瀏覽器是否一定會先重繪：**UNKNOWN**。若實機看不到文案，S8a 可以改為注入一個延後到下一次畫面更新的 `setTimer`，client 不必修改。
5. **瀏覽器建表比 spike 慢。** 建表 1,343～1,427 ms，spike 的 Chromium Worker 中位數是 1,180 ms。推論是本機負載造成的：S4 回報的 Node 建表同樣比 spike 慢約 20%，而且兩邊的節點數完全相同。
6. **失敗碼比規格多。** 本段新增 `TIMEOUT`、`SOLVER_FAILED`、`ALREADY_SOLVED` 三個 client 端失敗碼，`CANCELLED` 則是規格原有的。這些碼只出現在 `HINT_FAILED`／`DEMO_FAILED` 的 `code` 欄位，reducer 不檢查 `code`，所以不影響 engine。
7. `scratch/s6-smoke/index.html` 是產生檔（208 KB），和 `smoke.js` 一樣只放在 scratch，不進版控。
8. 過程中沒有誤改範圍外的檔案，也沒有發現會影響 state 欄位、action、資料格式、24 朝向編號、RNG 或求解結果的問題。
