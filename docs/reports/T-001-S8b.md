## 4. 未預期發現

1. **規格 §9.2 第 3 點「U5 中心（往畫面前方＝下）→ M」在字面「純垂直螢幕拖曳」下無法觸發**：實測 `U` 面的 `down` 3D 方向（`FACE_AXES.U.down=[0,0,1]`）在目前 `baseViewDeg={x:-22,y:-34}` 基準視角下投影到螢幕的方向約為 `(-0.874, 0.486)`（斜向左下，非正下方），純垂直拖曳（dx=0,dy>0）與此候選方向的夾角約 60.9°，超過 `maxAxisAngleDeg=30°` 門檻，依 §9.2 第 2 點規則會被判定「手勢作廢」，而不是轉 `M`。已用 Playwright 直接對真實渲染結果與獨立重算的投影幾何交叉驗證（`scratch/s8b-check/run-output.txt` 的 `U5→down(literal)` 列），確認這不是 `gesture.js` 的實作錯誤，而是規格原文「往下」一詞對 U／R（非正對鏡頭的面）而言只是「大致方向」的口語敘述，實際手勢需沿著該面在畫面上呈現的斜向網格線滑動才會落在門檻內（若確實沿正確投影方向（斜向左下）拖曳，14 組精準對齊樣本已證實 100% 正確轉出 `M`）。**未修改規格或程式**，僅記錄；建議 systems-engineer／製作人在 M-03 真機測試時留意此點，必要時考慮：(a) 於規格文字加註「示意方向，實際請沿畫面上的貼紙格線滑動」，或 (b) 評估是否放寬 `maxAxisAngleDeg`（會犧牲誤觸防呆）。`U1→right`、`U3→right` 等水平方向因 U 面 `right` 投影恰好接近水平（cos≈0.97），純水平拖曳不受影響。
2. 開工前 `node build/bundle.js` 產物為 267,724 bytes（S8a 產物基準），本段驗證時重新 build 後為 312,367→342,033 bytes（過程中 S8c／S8d 平行進版），符合分派單交叉影響守則「共用產物，允許互相覆寫；驗證前自己先 build 一次再測」；驗證全程（含最後一次重 build 後重跑）皆 0 個 console error，未見其他段半成品造成的錯誤。
3. `.cube-scene`（`cube-view.js` 建立、S8a 所有）未列在 S8a 回報「DOM 掛載點」正式表格內，但本段需要一個「舞台可視範圍」的容器來掛 `pointerdown`／`pointermove`／`pointerup`／`pointercancel` 監聽器（判斷「貼紙上」vs「方塊外」）；本段選擇直接 `ctx.root.querySelector('.cube-scene')`（找不到則退回 `[data-cube-stage]`），只讀取既有 class 掛監聽器，不修改其 DOM 結構或內容，未違反 S8a 契約「其餘模組不要直接操作裡面的 DOM」（該條約束的是操作/改寫）。建議 S8a 負責人或 systems-engineer 之後把這個既有 class 補進正式的 DOM 掛載點表，或另外提供 `ctx.view` 存取子，讓依賴更明確（目前不影響功能，僅為文件完整性建議）。
4. `ctx.view.snapTo`／`nearestOrient` 的介面設計（見 `docs/reports/T-001-S8a.md`）在數學上是「以拖曳累積矩陣（從單位矩陣起算）直接比對 24 個朝向的絕對相機矩陣」；本段依分派單字面指示（「放開後以 `ctx.view.snapTo(nearestOrient, params.ui.snapAnimMs)` 吸附」）如實實作。經分析：若使用者在**已經**轉到非 0 朝向後再次拖曳，這個「絕對比對」在理論上可能與「相對於目前朝向再疊加旋轉」的直覺不完全一致（`ctx.view` 目前沒有暴露可組合目前朝向的相機矩陣存取子）。本段驗證的情境（含 T-UI-06／T-UI-23 對應行為）皆從 `orient=0` 的新局開始，測試結果正確；**多次連續拖曳（尤其在非 0 朝向下再拖曳）的視覺吸附是否完全符合直覺，屬本段未驗證的範圍**，記錄供 systems-engineer 評估是否需要在 `ctx.view` 增加能力（例如公開目前相機矩陣或提供朝向合成函式）。這不影響目前規格與測試的判定，僅為架構層面的延伸觀察。
